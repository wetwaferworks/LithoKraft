# F59-6: Packed12 "higher GPU time" investigation (0.0.1.59-b-packed12)

**Date:** 2026-10-17, 06:00–06:20 ET. **Machine:** TheWorkstation, RTX 3050 Ti Laptop (driver 617.42), ReBAR arena.
**Binary:** `build\Release\LithoKraft-0.0.1.59-b-packed12.exe`. Only `LL_VK_PACKED12=1` vs `=0` was switched.
**Method:** interleaved A/B runs, with the order alternating each pair (on/off, off/on, ...). There were 26 runs in total; the waiter checked that no gate.ps1 or LithoKraft-0.0.1.* bench was running first. Each run was launched with SW_SHOWNOACTIVATE (no focus stealing) and wrote its own `--log` and `--bench-json` to `R:\repos\LithoLattice-Workflow\scratch-f596`. Nothing in Pass2 was edited and nothing was rebuilt.
Raw data and parsers are on the box in `/workspace/vulkan-push/f596/` (`data/`, `parse.py`, `matched.py`).

## Verdict
**F59-6 is a measurement artifact, not a regression. Leave Packed12 on as it is.**
At matched draw counts Packed12 has **about 17% lower GPU ms** in every non-streaming scenario: it was lower in **121 of 121** matched windows, with paired t of -6.7 to -13. It also gives **higher fps and lower p99**. On the stream bench there is no significant difference (p > 0.1).

## Why 3.11 vs 2.29 appeared
1. The verify `gpu=` value is **one 120-frame window**: the last `vulkan perf:` line (`vk_renderer.cpp:878-886`; `perf_` is reset every 120 frames at line 893). It is not a whole-run average.
2. The stream bench is **non-stationary**. GPU ms rises almost linearly with chunk draws as the world streams in, from 0.1 ms at 50 draws to about 3 ms at 2,600 draws. The two runs' windows end at different load points because a run that does more frames gets an extra window. In the original logs, packed16's 10th window was **3.15 ms at 2,069 draws** (the same as packed12's final 3.11 at 2,639 draws). Its 11th, final window then happened to dip to 2.29. In the same verify run, 58-a (packed16 only) reported 3.29.
3. Single windows are very noisy. In this rerun the last-window values were on {2.38, 4.24, 3.40, 2.01} vs off {3.99, 3.51, 4.18, 4.35}, so the sign is the *opposite* of the original finding.

Caveats:
- The "still" scenes are **still streaming in at 25–40 s**, so draws climb until the end. Per-run means are confounded by how far loading got, and a faster run reaches later and heavier windows. That is why the decisive column compares windows **at the same index and draw count (±3%)**.
- With the current `settings.json` stream radius, `--test-world` and `--radius 8` render almost the same scene (same draw counts). That differs from the verify "testworld" (466 MB mesh), which used other options.
- At still r64, packed16's mesh (3,158 MB) overflows the 2,773 MB device budget, and **416 MB spills to host memory** ("new blocks spill to host memory"). Packed12 (2,669 MB) stays device-local, which accounts for part of the larger gap there: PCIe vertex fetch for the spilled blocks.

## Code review of the suspected causes
- **Timestamp scope (`vk_renderer.cpp:810-865`)**: TOP_OF_PIPE is written at command-buffer begin, *before* `recordCopies`; BOTTOM_OF_PIPE is written after the composite pass and grab. The submit waits on the acquire semaphore only at `COLOR_ATTACHMENT_OUTPUT` (line 335), and there are 2 frames in flight. So the interval also counts staging copies, swapchain-image wait, and overlap with the previous frame's tail. This shows in the data: at still r64, GPU ms (19.4) is *larger* than the frame time (15 ms). The number is latency through the pipe, not GPU busy time, and it is clock and present sensitive. That is noise, not a bias against Packed12.
- **12-byte stride fetch**: the attributes are R16G16 @0, R16 @4, R8G8B8A8 @6 and R8G8 @10, all naturally aligned to their component size. NVIDIA fetches arbitrary strides without penalty, and the data shows a net *gain* from about 25% fewer vertex bytes. No problem.
- **Shader decode (`chunk_vert_body.glsl`)**: Packed12 adds one AND and one shift (`aPosZL & 511u`, `>> 9u`) and drops one attribute (location 4). That is negligible ALU work and one fewer fetch.
- **Draws and binds**: same mesh set, same `vkCmdDrawIndexed` per mesh; `baseVertex = offset / 12` is exact because of the 192 alignment. Matched windows show identical draw counts. Arena alignment 192 (lcm(12,64)) is still cache-line aligned. Block count is lower with Packed12 (68 vs 82 blocks at r8). No adverse effect.
- **Upload path**: ReBAR in-place `packVertices12` is CPU-side and outside GPU ms. Copy time was 0.21 vs 0.15 ms/frame at r8: slightly more CPU work packing 12-byte vertices than a plain memcpy, but small and already inside an fps gain.

## Recommendations
1. **Packed12: leave as is (on by default).** It is a real GPU and fps win at the r8 gameplay target (+8% fps, −17% GPU ms at equal draws) and a big one at r64 (+13% fps, p99 43→25 ms, no host spill).
2. **Fix the metric, not the vertex** (optional, small, toggle-free since it is diagnostics only):
   - Have the verify script report the **whole-run GPU average** (or the mean of all windows) together with the **draws/frame** of the same window, and compare formats at matched draws. One trailing 120-frame window of a streaming bench is not a usable A/B number.
   - Optionally add a second timestamp pair that brackets only `drawChunks` (after `vkCmdBeginRenderPass`). This removes copy, acquire and overlap time and gives a true chunk-pass cost.
   - For GPU A/B, prefer a stationary scene that is fully loaded before measuring. For example, add a warm-up until draws are stable, or use `--bench 60` and take only the last 20 s.
3. Close F59-6 as "Discovered by Cortana review; Investigated by Cortana: artifact of single-window GPU sampling on a non-stationary bench; no code change." (This is a log-entry suggestion only. BUGFIX_LOG was not edited.)
